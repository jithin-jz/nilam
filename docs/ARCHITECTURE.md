# How Nilam is built

This is for people changing the code. For using the app, see the
[README](../README.md).

## One exe, compiled by Windows itself

`build.cmd` invokes `%SystemRoot%\Microsoft.NET\Framework\v4.0.30319\csc.exe` -
the C# compiler that ships as part of .NET Framework - and references assemblies
straight out of the GAC. There is no project file. The whole build is one command
and takes about a second.

That compiler implements **C# 5**. Newer syntax (`?.`, `$""`, `nameof`,
expression-bodied members, `out var`, pattern matching) does not compile.

Three details in `build.cmd` are not optional:

- **`/noconfig`.** Without it the compiler applies `csc.rsp`, which
  auto-references about forty legacy Framework assemblies. At least one now
  drags in the .NET Standard shim `System.ComponentModel.Primitives.dll`, and
  that assembly and `System.dll` hold type forwarders pointing at each other.
  The compiler rejects the cycle (`CS0731`) and then cannot resolve
  `ISupportInitialize`, which every WPF `Window` implements - so the build fails
  on the first line that mentions a window. `/noconfig` skips `csc.rsp`, making
  the curated list in `build.cmd` the complete reference set. Never add one of
  the small netstandard shims to it.
- **The individual `.winmd` references.** The media card needs
  `Windows.Media.Control`, and the unified `Windows.WinMD` facade is too old on
  many machines to contain it. So the build references
  `%SystemRoot%\System32\WinMetadata\*.winmd` directly, and `src\WinRtAsync.cs`
  hand-rolls the `IAsyncOperation` -> `Task` bridge that
  `System.Runtime.WindowsRuntime` would normally provide. That namespace first
  appeared in Windows 10 version 1809, which is why that is the minimum.
- **The quoting.** Every `set` uses the `set "NAME=value"` form and no path is
  expanded inside a parenthesised block. The script therefore works from a
  folder with `&` in its name (`C:\Users\R&D\...`) or under
  `Program Files (x86)`. The compiler options go through a response file for the
  same reason.

`build.cmd` also stamps the exe: it reads `VERSION` and generates the assembly
attributes, and embeds `assets\app.ico` and `app.manifest`. `VERSION` is the one
place the release number is written.

## The widgets are separate transparent windows

Each card is its own borderless, transparent WPF `Window`, built at runtime by
`XamlReader.Load` from a markup string in `src\Markup.cs`. Keeping the markup as
strings avoids needing a XAML compiler in the build. Only values the code owns
are substituted into the markup - sizes and theme colours. A file path is never
substituted in: an install folder containing `&` used to make the XAML
unparseable and kill the app at start-up.

`src\Native.cs` does the desktop integration through P/Invoke:

- `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` - the card never takes focus and never
  appears in Alt+Tab. Mouse clicks still arrive, which is why the media buttons
  and the wave scrubber work on a window that cannot be focused.

  The tool-window style is also what keeps taskbar tools from counting a card
  as an open app. TranslucentTB, for one, treats any `WS_EX_TOOLWINDOW` window
  as not visible, so its "desktop" appearance still applies while the cards are
  showing and no ignore rule is needed. Early versions gave every card the
  title `KiroDesktopWidgets` so such a rule could match it; the title has not
  mattered since, and the Notes card keeps the style for the same reason.
- `SetWindowPos(..., HWND_BOTTOM, ...)` - parks each card at the bottom of the
  z-order so every app window draws over it. That is what makes them feel like
  they live *on* the desktop rather than floating above everything.

A 3-second timer re-parks any unfocused card, because Explorer restarts,
wallpaper changes and display switches all reshuffle the z-order.

**Show Desktop is the exception, and `DesktopLayer` handles it.** Win+D works by
raising the desktop window (`Progman`, the one holding the icons) above every
window that cannot be minimised - and a card cannot be. Measured on Windows 11:
with Show Desktop on, `Progman` moves from the very back to in front of all
seven cards, and they stay hidden until some other window is activated.

The desktop window normally sits behind everything, including a window parked at
the bottom. So `DesktopLayer` keeps an invisible marker window parked there and
never moves it for any other reason. If the desktop is ever in front of the
marker, Show Desktop is on: the cards are lifted to the front of the ordinary
windows for as long as that lasts, and dropped back when it ends. A foreground
change is the cue to look, with the 3-second timer as a backstop. The cards
themselves cannot serve as the test, because lifting them would make it read
"off" again.

The design fails safe: if the check is ever wrong in the "off" direction the
cards simply behave as they did before. `src\DesktopLayer.cs` is the only place
that decides which of the two positions a card gets.

The notes card is the one exception: it is created as interactive so you can
type in it, and it drops back to the desktop layer as soon as focus leaves.

Because a card is never the active window, a right-click menu opened from it
would not see the outside click that should dismiss it. Before a menu opens, the
app takes the foreground on the notification icon's hidden window - the same
thing every notification-area menu has to do.

## Where the cards go

`LayoutPlanner` is pure arithmetic over rectangles, so every screen shape is
covered by tests rather than by borrowing laptops.

- On a screen tall enough for all four rows the cards form one block, vertically
  centred at the right edge.
- On a shorter one - 1080p at 150% scaling leaves 672 units and the block needs
  688 - the rows are split evenly across blocks placed side by side below the
  banner, instead of overlapping.
- A saved position is kept if at least half the card is still on *any* monitor's
  work area. Otherwise the card returns to its default spot. This is re-checked
  whenever the display configuration or the work area changes, not only at
  launch.

Units are WPF device-independent pixels. The process is **system-DPI aware**:
one scale factor applies to every monitor, which keeps saved positions
meaningful. The cost is that on a second monitor with a *different* scale
Windows stretches the cards, so they are slightly soft. Per-monitor awareness
would fix that but changes the units `Window.Left` and `Window.Top` are measured
in; it needs a mixed-DPI setup to test and has not been done.

## Why it stays small

Three choices keep the process small and nearly idle:

- **`RenderMode.SoftwareOnly`.** Hardware rendering maps the GPU driver stack
  into the process - measured at about 81 MB of extra private bytes on an Intel
  GPU. A handful of near-static cards do not need a GPU.
- **`/platform:x86`.** Measured 12 MB lower private bytes than x64 for identical
  behaviour, because pointers and the NGEN images are half the size.
- **P/Invoke instead of WMI or Windows Forms** for CPU, memory, disk, battery,
  monitors and the notification icon, so nothing wakes the WMI provider host
  every few seconds and no extra UI framework is loaded.

And one thing that is deliberately *absent*: **there is no `DropShadowEffect` on
the cards.** The original style had one. Each card's window is exactly the size
of the card, so the shadow was clipped at the window's edge and never appeared
around it - but WPF still re-ran the blur over the whole card, on the CPU,
whenever anything inside changed. What the shadow did do was show through the
translucent card from underneath, making it read as 80% opaque instead of the
71% in the markup. The background is now that measured result as a flat colour:
the same look, with nothing to re-blur.

Measured on a 1920x1200 display at 150%, nothing playing, both builds running
side by side over the same eight seconds:

| | CPU (share of one core) | Private bytes |
|---|---|---|
| 1.4.2, with the shadow | 2.34% | 64 MB |
| 2.0.0 | 0.20% | 51 MB |

Timers are deliberately coarse: 1s clock, 1s wave, 2s media poll, 3s stats,
15min weather.

## Three techniques worth knowing

**Letter tracking.** WPF has no `CharacterSpacing` property - that is UWP only.
The weekday banner therefore lays out one `TextBlock` per letter with a right
margin, which is continuous and exact. Weaving spacing characters into the
string was the first attempt, but it can only step tracking in whole-glyph
widths and could not hit the target spacing. `BannerText` decides what counts as
a letter: a script that cannot be cut up - Arabic, Hebrew, the Indic scripts,
Thai - is drawn as one run with no tracking.

**The media progress clock.** A player is allowed to report its position once and
never refresh it - Spotify stamps `Position = 0` at track start and leaves it
there for the whole track. So the wave keeps its own clock (`PlaybackClock`)
that advances only while playback is `Playing`, re-anchoring whenever the player
actually reports a changed position. That is correct both for players that
report live positions and for those that do not, and it makes a pause hold the
wave still instead of collapsing it to zero or letting it run ahead.

Seeking is gated on `Controls.IsPlaybackPositionEnabled`, which varies by player
- Chrome reports true, some players report false. The cursor reflects it so a
dead click is never invited. The transport buttons call the session shown on
the card and only fall back to a media key when there is no session.

**Writes that cannot half-happen.** `AtomicFile` writes to a sibling file,
flushes it, and swaps it in with one rename. Notes are saved 600 ms after the
last keystroke, and layout 400 ms after a drag ends, rather than on every
keystroke and every pixel.

## State

Everything lives in `%APPDATA%\Nilam` (see the README for the files).
Releases before 2.0 - when the project was called Desktop Widgets - used
`%LOCALAPPDATA%\KiroDesktopWidgets`; on first run `Store` copies layout, notes and
the weather location across and leaves a note in the old folder. The program
files of such an install lived in `%LOCALAPPDATA%\DesktopWidgets`; the installer
removes that folder when it installs to the default location, after carrying
over any font the user had added to it.

Set `NILAM_STATE_DIR` to run against a scratch folder. Such an instance
is a separate profile with its own single-instance lock, so it can run beside
the installed copy - which is how to try a change without touching your own
notes and layout.

## Releases

A release is a pushed tag (`v2.0.0`). `.github/workflows/release.yml` refuses to
publish unless the tag matches `VERSION`, the build is clean and the tests pass.
It then publishes the stamped `install.ps1`, the source archive, a portable zip
and `SHA256SUMS.txt`.

The one-line install and `nilam update` both read from `releases/latest`. A push
to `main` therefore reaches nobody until it is tagged.
